# 0006. Модульний моноліт, доменні події й фонові задачі

- Статус: прийнято
- Дата: 2026-11-27

## Контекст

Адмін-платформа додає кілька незалежних областей (доступи, журнал, медіа, події, записи). Мікросервіси
для однієї команди й однієї БД — передчасна складність, але «один великий модуль» швидко перетворюється
на клубок залежностей.

## Рішення

- API — модульний моноліт: `apps/api/src/modules/{iam,audit,media,events}`. Модуль імпортується
  лише через свій `index.ts`; `scripts/check-boundaries.mjs` (частина `pnpm lint`) падає на
  глибоких імпортах у чужий модуль.
- Спільна інфраструктура — `apps/api/src/platform`: `DomainEventBus`, `JobQueue`, `MediaUsageRegistry`,
  `CLOCK`, курсорна пагінація, декоратори доступу.
- Модулі спілкуються доменними подіями з типізованим payload (`DomainEventMap`): наприклад, `iam`
  публікує `user.blocked`, а `events` скасовує майбутні записи. Відправник не знає про отримувачів.
- Зараз шина й черга — in-process. Шлях масштабування: transactional outbox (подія пишеться в ту саму
  транзакцію, окремий воркер доставляє) і BullMQ/Redis для `JobQueue`. Інтерфейси для модулів не змінюються.
- Кожна сутність має `organizationId` зі значенням `default` — заготовка під кілька організацій
  без міграції даних.

## Наслідки

- Межі модулів перевіряються автоматично, а не домовленістю.
- In-process події не переживають падіння процесу між commit і обробником; для критичних реакцій
  (скасування записів) це прийнятно до переходу на outbox, бо обробник ідемпотентний і його можна
  повторити вручну.

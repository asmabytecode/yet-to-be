# 0002. SQLite зараз, план переходу на PostgreSQL

- Статус: прийнято
- Дата: 2026-11-26

## Контекст

На старті один інстанс API, невелике навантаження і бажання мінімальної інфраструктури
(ні окремого сервера БД, ні адміністрування). Водночас перехід на клієнт-серверну БД має бути
передбачуваним, без переписування бізнес-логіки.

## Рішення

SQLite-файл у volume (`better-sqlite3` через Prisma driver adapter, WAL). Правила, що тримають шлях
до PostgreSQL відкритим:

- доступ до БД — лише через репозиторії (`src/database/repositories`), без raw SQL у сервісах;
- ідентифікатори — UUID, генеруються в застосунку;
- enum-и як рядки з перевіркою в Zod/TypeScript (переносима схема);
- міграції — лише Prisma Migrate, запускаються окремим сервісом `migrate`;
- бекап — онлайн через `better-sqlite3 .backup()` (`pnpm db:backup`), не копіюванням файлу.

## Коли переходимо

Тригери: потрібно більше одного інстансу API, або часті конкурентні записи впираються в блокування
SQLite. Кроки — у [docs/scaling.md](../scaling.md#1-sqlite--postgresql).

## Наслідки

- Простий деплой і бекап; немає мережевих затримок до БД.
- Горизонтальне масштабування API неможливе, доки БД — локальний файл.

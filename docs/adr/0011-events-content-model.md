# 0011. Модель подій: чернетка → публікація, блоки, записи з місткістю

- Статус: прийнято
- Дата: 2026-11-27

## Контекст

Події — перший «контентний» модуль. Ті самі патерни (чернетка, публікація, блоки, конкурентне
редагування) знадобляться для інших сутностей, тому їх треба закласти правильно один раз.

## Рішення

- Машина станів у `packages/shared` (`EVENT_TRANSITIONS`): `draft → published → cancelled`,
  будь-що → `archived`, `published → draft`. Публікація лише повної події (`EVENT_INCOMPLETE` з переліком полів).
- Оптимістичне блокування: кожна зміна передає `version`; розбіжність → `409 EVENT_VERSION_CONFLICT`,
  UI пропонує оновити сторінку. Створення — з `Idempotency-Key` (подвійний клік не дублює подію).
- Наповнення — типізовані блоки (`text`, `agenda_item`, `speaker`, `link`) як discriminated union Zod.
  Дані блоку зберігаються JSON-ом і перевіряються і при записі, і при читанні. Markdown — без сирого HTML;
  на сайті рендериться `react-markdown` з `skipHtml`, лише `https:`/`mailto:` посилання.
- М'яке видалення з step-up; опубліковану подію спершу знімають з публікації або скасовують.
- Записи: одна пара (подія, користувач) — один рядок (`@@unique`). Місткість гарантує атомарний
  `UPDATE events SET registeredCount = registeredCount + 1 WHERE capacity IS NULL OR registeredCount < capacity`
  у тій самій транзакції, що й рядок запису. Це коректно і в SQLite, і в PostgreSQL (рядок події
  блокується), тож переповнення неможливе навіть під паралельними запитами.
- Запис закривається з початком події. Блокування акаунта скасовує його майбутні записи (доменна подія).
- Публічні відповіді: `Cache-Control: public, max-age=0, s-maxage=60` — CDN кешує, браузер перепитує.

## Наслідки

- Лічильник `registeredCount` — денормалізація; джерело правди — рядки записів, тож за потреби
  лічильник перераховується одним запитом.
- Зменшити місткість нижче кількості записаних не можна (`400`, поле `capacity`).

# 0003. Токени в httpOnly cookies, а не в localStorage

- Статус: прийнято
- Дата: 2026-11-26

## Контекст

SPA потрібна сесія. Поширений підхід — JWT у `localStorage` і заголовок `Authorization`. Але будь-який
XSS (вразлива залежність, помилка в шаблоні) тоді дає зловмиснику токени, які він може вивезти й
використовувати поза браузером жертви.

## Рішення

- Access token (JWT, 15 хв) і refresh token (випадковий, 30 днів, у БД лише SHA-256) — у cookies
  `HttpOnly`, `SameSite=Strict`; через https — ще й `Secure` з префіксами `__Host-`/`__Secure-`.
- Refresh-cookie має `Path=/api/v1/auth` — браузер не надсилає її на інші маршрути.
- CSRF: double-submit (`ytb_csrf` читається JS і дублюється в `X-CSRF-Token`) + перевірка `Origin`
  і `Sec-Fetch-Site`.
- Ротація refresh-токена з виявленням повторного використання: повтор старого токена відкликає весь
  ланцюжок сесій.
- Фронтенд і API на одному origin (Nginx / Vite proxy), тому CORS не вмикається.

## Наслідки

- JS не бачить токенів навіть при XSS; E2E-сценарій 8 це перевіряє.
- Потрібен CSRF-захист на всіх мутаціях (глобальний `CsrfGuard`).
- Інші сервіси не можуть перевіряти токени самостійно; коли знадобиться — JWKS (docs/scaling.md).
